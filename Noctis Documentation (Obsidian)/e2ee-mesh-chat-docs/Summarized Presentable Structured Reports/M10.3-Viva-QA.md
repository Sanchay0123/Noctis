# M10.3 Viva Q&A
## End-to-End Encrypted Messaging System over a Decentralized Mesh Network

### Q1. Why use a decentralized mesh?
A mesh distributes forwarding responsibility across peers and avoids dependence on a single central messaging server.

### Q2. Why is E2EE important in a mesh?
Intermediate peers are not trusted with application plaintext. E2EE keeps the message content protected from those relays.

### Q3. Why Ed25519?
It provides compact public keys and efficient digital signatures suitable for identity authentication.

### Q4. Why X25519?
It provides an efficient elliptic-curve Diffie-Hellman key-agreement mechanism for deriving a shared secret from ephemeral keys.

### Q5. Why ChaCha20-Poly1305?
It provides authenticated encryption, combining confidentiality and integrity in one standard AEAD construction and performing well in software.

### Q6. Why HKDF?
The raw key-agreement output is transformed into purpose-specific directional session keys through a standard extract-and-expand KDF.

### Q7. What does TOFU protect against?
After an identity has been trusted, TOFU can detect a later change to the stored peer identity.

### Q8. What does TOFU not protect against?
It does not authenticate first contact against an active MITM attacker because there is no prior trusted identity anchor.

### Q9. Does the project provide perfect forward secrecy?
The design uses ephemeral X25519 session keys, but the project does not claim Signal-style post-compromise security or a continuously ratcheted key schedule.

### Q10. What does a relay see?
A relay can see routing metadata such as source/destination identifiers, packet identifiers, TTL and packet type, along with opaque ciphertext. It does not receive the endpoint application plaintext.

### Q11. Why can't an intermediate relay decrypt Alice-to-Carol traffic?
The endpoint ciphertext is protected under the Alice–Carol session keys. The relay does not possess those endpoint keys.

### Q12. What is bounded managed flooding?
A packet is forwarded through eligible peers, with TTL, duplicate suppression, queue bounds and peer limits preventing unbounded propagation.

### Q13. Why TTL?
TTL limits how long a packet can propagate and prevents indefinite circulation through loops.

### Q14. How does duplicate suppression work?
A node maintains a bounded seen-cache. A packet already observed under the same `(source_node, packet_id)` identity is not forwarded again.

### Q15. Why is the cache key a tuple?
PacketID is generated locally by a source node and is not claimed to be globally unique. The source identity distinguishes otherwise identical local packet identifiers.

### Q16. Why bound queues and handshakes?
Unbounded resources could be abused to consume memory, goroutines, sockets or processing capacity. Bounds provide a basic resource-exhaustion defense.

### Q17. Why a 64 KiB frame limit?
It provides a deterministic upper bound on accepted framed input and limits memory exposure from oversized network input.

### Q18. How is replay prevented?
Application messages carry sequence numbers. The receiving cryptographic layer maintains a replay window and rejects already accepted or stale sequence numbers.

### Q19. What happens when ciphertext is modified?
Authenticated decryption fails because the AEAD authentication check no longer validates.

### Q20. What happens when a handshake signature is invalid?
The handshake is rejected and the node does not establish the authenticated session represented by that invalid transcript.

### Q21. What are the major non-goals?
Perfect anonymity, global traffic-analysis resistance, complete metadata hiding, deniability, compromised-endpoint protection, guaranteed delivery, and production-scale routing/DoS security.

### Q22. Why are the latency results not Internet performance?
They were measured on `127.0.0.1`, so they do not include realistic Internet propagation, congestion, jitter, packet loss, or WAN routing.

### Q23. Why was AEAD decryption not benchmarked?
The initial isolated benchmark repeatedly presented sequence numbers that the production replay protection correctly rejected. The result therefore measured replay rejection rather than valid decryption and was discarded.

### Q24. Why is concurrent handshake scaling not claimed?
The campaign performed 50 sequential handshakes. It did not perform a parallel concurrency experiment.

### Q25. What did M9 validate?
M9 validated security demonstrations including wrong-peer rejection, tampering rejection, replay rejection, signature failure, malformed packets, TTL, duplicate suppression, pending-handshake bounds, relay blindness, and GUI behavior.

### Q26. What did M10.2 validate?
M10.2 established a local baseline for application latency, throughput, message-size handling, resource measurements, cryptographic operation timings, and handshake repeatability.

### Q27. What is the biggest routing limitation?
Managed flooding can generate redundant traffic as topology size and density increase. It trades routing simplicity for network efficiency.

### Q28. Why not use a DHT?
A DHT or more sophisticated routing system was outside the implemented M6 scope. It remains a possible future direction.

### Q29. What is the measured 1 KiB throughput?
Approximately 1,854 successfully delivered application messages per second in the local loopback experiment, with 5,000/5,000 delivered.

### Q30. What is the measured 1 KiB multi-hop latency?
Mean 0.122 ms and P99 0.408 ms in the tested Alice–Bob–Carol loopback topology.

### Q31. What is the largest tested application payload?
60 KiB, with 100/100 successful trials in the tested single-hop experiment. It is not claimed as the absolute protocol maximum.

### Q32. What is the pending-handshake limit?
The implemented production limit is 10 pending handshakes, validated in M9.2.

### Q33. What would you improve next?
I would investigate WAN/network impairment testing, larger mesh topologies, more efficient routing, richer metadata protection, post-compromise security, persistent messaging, and concurrent handshake performance.

### Q34. What is the key security principle of the architecture?
Routing and endpoint cryptography are separate. A relay can forward the packet without needing the endpoint session keys or application plaintext.
