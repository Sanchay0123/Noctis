# Presentation Outline: Design and Implementation of an End-to-End Encrypted Messaging System over a Decentralized Mesh Network

## Slide 2: Problem Statement
- **Points**:
  - Centralized messaging systems create single points of failure.
  - Heavy reliance on trusted third-party infrastructure.
  - Vulnerability to localized censorship and central data breaches.
- **Speaker Notes**: Highlight the systemic risks of centralization and the motivation for building a robust alternative capable of secure operation without central servers.

## Slide 3: Motivation & Objectives
- **Points**:
  - **Motivation**: Enable resilient, decentralized communication for privacy-conscious environments and ad-hoc networks.
  - **Objectives**:
    - Implement bounded managed flooding for routing.
    - Guarantee confidentiality and integrity via E2EE.
    - Establish cryptographically bound identities.
- **Speaker Notes**: Outline what the project set out to achieve, emphasizing the balance between resilient routing and strict cryptographic constraints.

## Slide 4: Threat Model
- **Points**:
  - **Mitigated Threats**: Traffic observation, ciphertext capture, modification, replay, impersonation.
  - **Explicit Non-Goals**: Perfect anonymity, global traffic-analysis resistance, guaranteed delivery, compromised endpoint protection.
- **Speaker Notes**: Clearly define the threat model. Stress that the system ensures payload confidentiality and integrity, but metadata visibility to intermediate relays is an acknowledged architectural trade-off.

## Slide 5: Proposed Architecture
- **Points**:
  - Layered architecture separating UI, Cryptography, Routing, and Transport.
  - UI strictly interfaces with the `ApplicationService`.
  - Routing handles opaque packets.
- **Diagram**: 
  ```mermaid
  graph TD
      User[User / UI] --> AppSvc[ApplicationService]
      AppSvc --> Session[Session / Crypto]
      Session --> Routing[Routing]
      Routing --> Transport[Transport]
      Transport --> Peers[Mesh Peers]
  ```
- **Speaker Notes**: Explain the separation of concerns, noting how the cryptography layer encapsulates application data before it ever reaches the routing tier.

## Slide 6: Decentralized Mesh Network
- **Points**:
  - Ad-hoc peer-to-peer TCP connections.
  - Strict 64 KiB framing constraint on transport.
  - `peerManager` oversees concurrency limits and socket lifecycles.
- **Speaker Notes**: Describe how nodes physically connect. The 64 KiB limit provides a deterministic boundary for memory allocations during socket reads.

## Slide 7: Protocol & Packet Flow
- **Points**:
  - **Bounded Managed Flooding**: Messages are broadcast to all peers except the origin.
  - **Duplicate Suppression**: Seen-cache uses `(source_node, packet_id)`.
  - **TTL Enforcement**: Drops looping or old packets.
- **Speaker Notes**: Emphasize that the project does NOT use a DHT or complex route discovery. Bounded managed flooding trades network efficiency for routing simplicity and resilience against route manipulation.

## Slide 8: Cryptographic Design
- **Points**:
  - **Identity**: Ed25519 asymmetric signatures.
  - **Key Agreement**: X25519 ECDH.
  - **KDF**: HKDF-SHA-256.
  - **AEAD**: ChaCha20-Poly1305.
- **Speaker Notes**: Detail the modern cryptographic primitives selected. The system relies entirely on standard, well-analyzed algorithms to construct its security boundaries.

## Slide 9: Secure Session Establishment
- **Points**:
  - **Handshake**: `INIT` and `RESP` exchange.
  - **Binding**: Handshake artifacts are signed by long-term Ed25519 identity keys.
  - **Trust Model**: Trust On First Use (TOFU).
- **Diagram**:
  ```mermaid
  sequenceDiagram
      Alice->>Bob: INIT (Ephemeral Key A, Signed)
      Bob->>Alice: RESP (Ephemeral Key B, Signed)
      Note over Alice,Bob: Derive Session Keys (HKDF)
  ```
- **Speaker Notes**: Describe the key exchange. Mention that TOFU protects against subsequent identity spoofing but relies on safe initial contact.

## Slide 10: Security Controls
- **Points**:
  - Semantic protobuf validation drops malformed packets.
  - ChaCha20-Poly1305 MAC validates payload integrity.
  - Sequence-based nonces mapped to a sliding window reject replay attacks.
  - Concurrency bounded by `MaxPendingHandshakes = 10`.
- **Speaker Notes**: Walk through the layered defenses. Network filters drop oversized frames, Routing drops duplicates, Crypto drops tampered/replayed ciphertexts.

## Slide 11: Security Validation / Attack Demonstrations
- **Points**:
  - Milestones 9.2 & 9.3 validated theoretical controls against active implementation.
  - **Demonstrated Rejections**: Wrong PeerID, modified ciphertext, replay attempts, invalid signatures.
  - GUI validated secure rendering of identities and sessions.
- **Speaker Notes**: These are not just theoretical constructs; the implementation physically rejects the documented threats, proving the integration is structurally sound.

## Slide 12: Experimental Methodology
- **Points**:
  - Measured local loopback performance to isolate application logic from WAN interference.
  - Captured metrics: Direct Latency, Multi-Hop Latency, Delivery Throughput, Resource Usage.
  - Excluded warm-up and session establishment anomalies from measurements.
- **Speaker Notes**: Frame the context of the experiments. Clarify that this is a baseline performance analysis of the software stack itself, not an Internet deployment benchmark.

## Slide 13: Experimental Results
- **Points**:
  - **Throughput**: ~1,854 messages/sec (1KiB) delivery over 2.69 seconds (0 loss).
  - **Multi-Hop Latency (Alice→Bob→Carol)**: 1KiB Mean = 0.122 ms, P99 = 0.408 ms.
  - **Mesh Forwarding**: Validated structural relay blindness (Bob relays but cannot decrypt).
  - **Scale**: 60KiB maximum tested payloads successfully traversed the frame constraint.
- **Speaker Notes**: Present the quantitative findings. Highlight the sub-millisecond latencies and the reliable throughput achieved by the application logic.

## Slide 14: Limitations & Future Work
- **Points**:
  - **Limitations**: No WAN latency/jitter, perfect anonymity, or concurrent handshake scaling measured. AEAD decryption benchmark discarded due to replay constraints.
  - **Future Work**: Network impairment testing, larger mesh topology profiling, route optimization research, richer metadata protection.
- **Speaker Notes**: Honestly address what the system does not do. Position these limitations as the immediate stepping stones for future academic or practical work.
