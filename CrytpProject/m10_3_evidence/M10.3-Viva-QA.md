# Viva Q&A: End-to-End Encrypted Messaging System over a Decentralized Mesh Network

**Q1: Why choose a decentralized mesh network over a traditional client-server architecture?**
**A**: Decentralized architectures eliminate single points of failure and central honeypots for data breaches. They distribute routing responsibilities across peers, making the network highly resilient for ad-hoc, localized, or censorship-resistant environments.

**Q2: Why is End-to-End Encryption (E2EE) necessary in this mesh?**
**A**: Because intermediate routing nodes (peers) are fundamentally untrusted. E2EE ensures that while an intermediate node can forward a packet, it cannot read the application payload.

**Q3: Why use Ed25519 for identity?**
**A**: Ed25519 provides fast, highly secure asymmetric digital signatures with small key sizes (32 bytes), making it ideal for embedding identities efficiently within protocol handshakes without excessive packet overhead.

**Q4: Why use X25519 for key agreement?**
**A**: X25519 is an Elliptic-Curve Diffie-Hellman (ECDH) function that is extremely fast, avoids timing side-channel attacks, and securely derives a shared secret over an untrusted channel.

**Q5: Why select ChaCha20-Poly1305 over AES-GCM?**
**A**: ChaCha20-Poly1305 is a software-optimized Authenticated Encryption with Associated Data (AEAD) cipher that performs exceptionally well on devices without dedicated AES hardware instructions, providing both confidentiality and MAC-based integrity.

**Q6: What is the purpose of HKDF in your cryptographic design?**
**A**: The HMAC-based Extract-and-Expand Key Derivation Function (HKDF) safely transforms the raw ECDH shared secret into cryptographically strong, independent, and uniform symmetric session keys for bidirectional communication.

**Q7: What does Trust On First Use (TOFU) protect against?**
**A**: TOFU protects against subsequent identity spoofing or tampering once the initial key is saved. The system alerts the user if the peer's underlying public key changes in the future.

**Q8: What does TOFU NOT protect against?**
**A**: TOFU does not protect against an active Man-In-The-Middle (MITM) attack during the very first connection, because there is no prior trust anchor or global PKI to verify the initial key exchange.

**Q9: Does this design offer perfect forward secrecy?**
**A**: No. While session keys are ephemeral, a compromise of the long-term identity keys could theoretically allow impersonation going forward. True perfect forward secrecy generally requires continuous key ratcheting (like the Signal Protocol), which is outside our current scope.

**Q10: What metadata does an intermediate relay see?**
**A**: A relay sees the packet type, source and destination NodeIDs, PacketID, TTL, and the opaque ciphertext. It cannot see the plaintext application payload.

**Q11: Why can't Bob decrypt Alice-to-Carol traffic when routing it?**
**A**: The application payload is encrypted using symmetric session keys derived strictly from Alice and Carol's private endpoints. Bob only possesses the opaque `APP_DATA` packet and lacks the requisite cryptographic material to decrypt it.

**Q12: What is bounded managed flooding?**
**A**: It is a routing strategy where nodes broadcast incoming packets to all connected peers except the sender, bounded strictly by a Time-To-Live (TTL) field and duplicate suppression caching to prevent infinite routing loops.

**Q13: Why is TTL required in flooding?**
**A**: TTL (Time-To-Live) ensures that packets eventually expire and are dropped from the network, preventing them from consuming bandwidth indefinitely if they get stuck in a routing loop.

**Q14: How does PacketID duplicate suppression work?**
**A**: Each node maintains a seen-cache of recent packets. If a node receives a packet it has recently forwarded, it drops it immediately instead of rebroadcasting it, terminating redundant flooding paths.

**Q15: Why is the seen-cache key `(source_node, packet_id)` rather than just `packet_id`?**
**A**: Because `PacketID` is generated locally by the source node and is not globally unique. The combination of the source's identity and its local counter creates a probabilistically unique key across the mesh.

**Q16: Why enforce bounded queues and concurrent handshakes?**
**A**: To mitigate resource exhaustion and Denial-of-Service (DoS) attacks. Without bounds, a malicious node could flood the network with handshake requests or oversized queues, crashing the application.

**Q17: Why enforce a strict 64KiB transport frame limit?**
**A**: A deterministic upper bound prevents malicious peers from sending infinitely large packets to cause Out-Of-Memory (OOM) crashes during TCP reads.

**Q18: How is message replay prevented at the cryptographic layer?**
**A**: The AEAD implementation utilizes sequence-based nonces tied to a sliding replay window. Any ciphertext arriving with a sequence number already recorded in the window (or too old) is rejected.

**Q19: What happens if an intermediate node modifies the ciphertext?**
**A**: The Poly1305 MAC tag verification will fail upon arrival at the destination endpoint, and the cryptographic layer will drop the tampered packet, returning a decryption error.

**Q20: What happens if a signature is invalid during the handshake?**
**A**: The session initialization aborts immediately. The node refuses to derive session keys or allocate session state for an unverified identity.

**Q21: What are the system's explicit non-goals?**
**A**: Perfect anonymity, global traffic-analysis resistance, complete metadata hiding, post-compromise endpoint protection, deniability, and guaranteed delivery over unreliable links.

**Q22: Why aren't the local latency experimental results indicative of Internet performance?**
**A**: The experiments were conducted on a loopback interface (`127.0.0.1`), effectively isolating the software stack's processing overhead. Real Internet deployments would incur significant physical latency, packet loss, and jitter.

**Q23: Why is AEAD decryption performance classified as NOT MEASURED?**
**A**: Attempting to benchmark isolated decryption iteratively fed the same sequence numbers into the production stack, immediately triggering the sliding replay-protection window. Bypassing this would require modifying production security code, which violates the audit constraints.

**Q24: Why isn't concurrent handshake scaling claimed in the results?**
**A**: The experimental campaign executed 50 handshakes sequentially (Handshake Repeatability). It did not test parallel, concurrent handshake loads, so scaling limits beyond the theoretical `MaxPendingHandshakes=10` bound were not empirically measured.

**Q25: What did Milestone 9 (M9) validate?**
**A**: M9 validated the structural security boundaries: proving wrong PeerIDs are rejected, tampered ciphertexts drop, replays fail, TTLs are enforced, duplicates are suppressed, and the UI accurately reflects identity state.

**Q26: What did Milestone 10.2 validate?**
**A**: M10.2 validated baseline application-level throughput, latency, and memory performance constraints of the unmodified codebase in an isolated local environment.

**Q27: What is the most significant limitation of the current implementation?**
**A**: The routing protocol relies on naive flooding, which scales poorly in large, dense networks due to massive packet duplication. It trades network efficiency for discovery simplicity.

**Q28: How would you improve the routing protocol next?**
**A**: Future work would explore replacing simple flooding with distance-vector or link-state routing, or implementing a Distributed Hash Table (DHT) for efficient peer discovery and targeted packet routing.
